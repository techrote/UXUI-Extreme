## Remaining risks / explicit limits

1. **External links and status drift:** documentation CI checks only repository-local Markdown paths/anchors. GitHub module PR, issue, release and CI states must be checked again manually (or in a separately approved online audit) before acceptance or integration.
2. **Windows UI reality:** no Windows GUI, high-DPI, multi-monitor, accessibility, crash-recovery, taskbar restore, visual-fidelity or Explorer injection tests were run by this umbrella-documentation pass.
3. **Release-level vs feature-level acceptance:** release notes report beta/delta daily owner testing, but an independently linked PASS for every UX-012–017 feature was not re-established by this audit.
4. **Residual functionality:** brightness-based tray inversion, low-contrast warnings, arbitrary external private-font workflows, Open-Shell Start-button integration, jump lists, maximise-only auto-hide, and whole-window skinning are not declared complete.
5. **Scope:** existing module application code and build workflows were not modified; any genuine runtime defect should be fixed behind its own module issue, branch and PR, with exact-head CI plus Windows acceptance where appropriate.

## Automated qualification

Run `python3 -m unittest discover -s tests -v` followed by `python3 scripts/check_docs.py` from the umbrella root. GitHub Actions runs the same steps on PRs and pushes to main. These are unit and documentation-integrity checks, not application acceptance.

## Maintaining the result

For every module change: verify its PR/issue status and checked SHA, capture release provenance, update [PROGRAMME.md](PROGRAMME.md), [PARITY.md](PARITY.md) if feature coverage changed, and [RAG.md](../RAG.md) when architecture changed. Distinguish "merged", "CI green", "release-noted owner use", and "feature-specific owner PASS".
